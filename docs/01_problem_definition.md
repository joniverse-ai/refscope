## 1. 도메인 설명

**브랜드·상품 디자인.** 정확히는 내 도메인 정의문 그대로다.

> 나는 상품이 하고싶어 하는 말을 소비자에게 디자인으로 쉽게 전달하는 사람이다.

이 일의 작업 흐름은 매번 같은 네 단계를 돈다.

```
리서치  →  핵심 메시지 도출  →  비주얼 전환  →  가이드라인 문서화
  ↑
여기가 이번 PoC의 표적
```

리서치는 모든 프로젝트의 0번째 단계다. 새 브랜드를 잡든, 시즌 상세페이지를 갈아엎든, 카테고리를 옮기든, 항상 먼저 묻는다 — **"이 카테고리 브랜드들은 지금 소비자에게 뭐라고 말하고 있나?"** 남들이 이미 점유한 말과 색을 알아야 내 브랜드가 설 자리가 보인다.

현재 진행 중인 실제 프로젝트 [단정 · Danjeong](https://joniverse-ai.github.io/danjeong/)(B2B 프리미엄 답례 선물 셀렉트샵)이 이 PoC의 실전 무대다. 프리미엄 기프트·전통 디저트 카테고리의 레퍼런스를 훑어야 하는 상황이 실제로 걸려 있다.

## 2. 현재의 문제

### 지금의 작업 흐름 (as-is)

레퍼런스 사이트 **1개당** 이 순서를 반복한다.

| # | 하는 일 | 성격 |
|---|---|---|
| 1 | 검색으로 후보 브랜드를 찾는다 | 판단 |
| 2 | 사이트에 들어가 상세페이지를 끝까지 스크롤한다 | 노동 |
| 3 | 화면을 나눠 캡처하고 파일명을 정리한다 | 노동 |
| 4 | **헤드라인·서브카피를 손으로 옮겨 적는다** | 노동 |
| 5 | 스포이드로 주요 색을 찍어 팔레트를 메모한다 | 노동 |
| 6 | 섹션 구성 순서를 적는다 (히어로 → 브랜드 스토리 → 성분 → 사용법 → 후기 …) | 노동 |
| 7 | 노션/슬라이드에 카드로 정리한다 | 노동 |
| 8 | **"그래서 공통 패턴이 뭐고, 빈 자리가 어디인가"를 도출한다** | 판단 |

사이트 1개에 `[측정]`분. 10~20개를 보려면 하루가 통째로 날아간다.

### 병목의 정체 — 왜 하필 이 도메인에서 이게 힘든가

**한국 상세페이지는 대부분 긴 이미지 한 장이다.** 디자이너가 포토샵에서 만든 세로로 긴 JPG를 그대로 올리는 것이 이 시장의 관행이다. 그 결과:

- 브라우저에서 `Ctrl+F`가 걸리지 않는다
- 카피를 **드래그해서 복사할 수 없다**
- 텍스트 색·크기가 CSS가 아니라 픽셀에 구워져 있다

즉 **문서가 아니라 사진으로 존재하는 정보**다. 그래서 4번(카피 옮겨 적기)이 자동화되지 않고, 사람이 화면을 보며 타이핑하는 전사(轉寫) 노동으로 남는다. 5번(스포이드)도 같은 이유다.

### 얼마나 심한가 — 직접 재봤다

이건 인상이 아니라 측정값이다. 평가셋 12개 페이지를 수집해 **"세로 영역 중 몇 %가 'DOM 텍스트 0자 + 큰 이미지가 덮음' 상태인가"** 를 쟀다. (`uv run refscope analyze`로 재현 가능)

| 페이지 종류 | 개수 | 글자가 이미지에 갇힌 비율 (평균) |
|---|---|---|
| 브랜드 홈 | 7 | **2%** |
| 상품 상세 | 5 | **81%** |

개별 상세페이지:

| 브랜드 | 페이지 높이 | 이미지에 갇힌 비율 |
|---|---|---|
| 강릉명일한과 (한과다오) | 44,491px | **92%** |
| 바른손더기프트 | 32,337px | **87%** |
| 한품 (99플라워) | 12,868px | **78%** |
| 교동한과 (만월) | 17,275px | **75%** |
| 서울쿠키 (무궁화세트) | 12,036px | **75%** |

교동한과 상세페이지는 본문 전체가 `500 × 8,555px` 통이미지 **한 장**이다. 페이지에서 긁히는 DOM 텍스트 2,140자는 전부 헤더·푸터·약관이었다.

두 가지가 이 표에서 확정된다.

1. **병목은 상세페이지에만 있다.** 홈은 2%라 DOM 추출로 충분하다. 상세는 81%라 OCR 없이는 카피의 5분의 4를 못 읽는다. → 파이프라인이 페이지마다 읽는 방법을 바꿔야 하는 이유.
2. **길이 자체가 노동이다.** 상세페이지 평균 약 24,000px — 1,440px 화면으로 **17번 스크롤**해야 끝까지 본다. 사람이 이걸 5개만 봐도 지친다.

> 4회차 마지막 절 제목이 이 상황의 정확한 요약이다 — **"넘긴 것은 노동이고 남은 것은 결정입니다."**
> 지금은 2~7(노동)에 시간을 다 쓰고, 정작 값이 나오는 8(판단)은 지쳐서 감으로 때운다.

### 정보가 부족한 게 아니다

레퍼런스는 인터넷에 넘친다. 부족한 것은 **비교 가능한 형태로 정렬된 레퍼런스**다. 20개 사이트를 봐도 머릿속에만 남으면 "공통 패턴"을 말할 수 없다. 지금 내 리서치 결론이 근거보다 인상에 기대는 이유가 여기 있다.

## 3. 개선 가설

> **화면에 사진으로 갇혀 있는 정보를 기계가 읽어내 표로 만든다.**
> URL 목록만 주면 캡처·전사·색 추출·구조 분류까지 끝난 리서치 카드가 나온다.
> 사람은 8번(판단)에서 시작한다.

### 파이프라인

```
[refs.yaml : URL 목록]
        │
        ▼
 ① 풀페이지 캡처 (Playwright)  ─────────▶ 스크린샷 + DOM 텍스트 + computed style
        │
        ├─ DOM에 텍스트가 있다  ──▶ 무손실 추출 (색·크기까지 정확)
        └─ 통이미지다 (텍스트 없음) ──▶ ② OCR (글자 + 위치 + 크기)
        │
        ▼
 ③ VLM — 섹션 구조·톤·비주얼 요소 서술 (통이미지를 사람처럼 읽기)
        │
 ④ 컬러 팔레트 추출 (k-means) + 타이포 크기 분포
        │
 ⑤ 카피 문장 임베딩 → 클러스터링 → 메시지 유형 분류
        │
        ▼
[출력] 브랜드별 리서치 카드 HTML + 카테고리 비교표 + 팔레트 무드보드 + 공통 패턴 요약
```

### 이 PoC의 핵심 판단: 세 가지 눈을 조건에 따라 갈아 끼운다

같은 페이지라도 **DOM 텍스트 / OCR / VLM** 중 무엇으로 읽느냐에 따라 얻는 것이 다르다.

| 눈 | 얻는 것 | 못 얻는 것 |
|---|---|---|
| DOM 텍스트 | 글자·색·크기가 **무손실** | 통이미지 페이지에서는 아무것도 |
| OCR | 이미지 속 글자와 그 **위치** | 왜 그렇게 배치했는지 |
| VLM | 구조·톤·분위기 **서술** | 글자 정확도는 OCR보다 낮을 수 있음 |

그래서 파이프라인 1단계는 모델이 아니라 **검사**다 — DOM에 텍스트가 있으면 OCR을 돌리지 않는다. 정확한 원본을 흐릿한 사본으로 바꾸는 짓이기 때문이다. *(4회차 6절 「같은 PDF를 네 가지 눈으로 읽기」가 그대로 이 설계다. 여기서는 PDF 대신 웹페이지다.)*

### 커리큘럼과의 연결

| 회차 | 내용 | 이 PoC에서 쓰는 곳 |
|---|---|---|
| 4-2 | 글자를 꺼내는 길, OCR 조립 라인 | 통이미지 상세페이지에서 카피 추출 |
| 4-4 | 이미지와 언어를 함께 보는 모델(VLM) | 섹션 구조·톤 서술 |
| 4-6 | 같은 PDF를 네 가지 눈으로 읽기 | DOM/OCR/VLM 비교 실험 그 자체 |
| 4-3, 4-7 | 찾아내기와 경계 긋기 (YOLO/SAM) | (확장) 제품컷 영역만 잘라 무드보드 컷아웃 |
| 2-6·7 | 토큰과 컨텍스트 / 토큰 예산표 | 페이지 20개 분량을 요약에 넣는 청킹 |
| 3-5·8 | 데이터는 어디에 남는가 / 실행 위치 결정문 | 전 파이프라인 로컬 실행 결정 |

## 4. 대상 사용자

- **1차: 나 자신.** 프로젝트 착수 때마다 이 리서치를 반복하는 브랜드·상품 디자이너.
- **2차**: 소규모 브랜드팀의 디자이너·마케터·기획자. 리서처를 따로 둘 수 없어 디자이너가 리서치까지 겸하는 조직.
- **사용 시점**: 프로젝트 착수 시 1회 배치 실행(수 분) → 결과 카드를 놓고 회의. 실시간 처리는 필요 없다.

## 5. 성공 기준

| # | 지표 | 기존 방식 | 목표 | 측정 방법 |
|---|---|---|---|---|
| 1 | **사이트 1개 정리 시간** | `[측정]`분 (수작업) | **3분 이내** | 스톱워치 실측, 사이트 3개 평균 |
| 2 | **카피 추출 재현율** | 사람이 하면 100%, 단 전량 타이핑 | 정답 카피의 **80% 이상** 자동 추출 | 내가 손으로 적은 정답(`labels/copy.yaml`)과 문자열 대조 |
| 3 | **브랜드 컬러 재현** | 스포이드로 3색 | 내가 찍은 주요 3색 중 **2색 이상**이 자동 팔레트 top-8에 포함 (ΔE < 10) | CIEDE2000 색차 계산 |
| 4 | **섹션 구조 분류 정확도** | 사람이 눈으로 | 정답 라벨 대비 **70% 이상** | 섹션별 라벨(`labels/sections.yaml`) 대조 |
| 5 | **전체 리서치 소요 시간** | `[측정]`분 (사이트 10개) | **15분 이내** (실행 + 검토) | 실측 |

**정성 검증**: 사이트 3개를 골라 ① 내 수작업 리서치 노트 ② PoC 리서치 카드를 나란히 놓고 무엇이 남고 무엇이 빠졌는지 서술한다. **실패 사례를 반드시 함께 기록한다** — 어떤 페이지에서 OCR이 무너지는지, VLM이 무엇을 지어내는지.

## 6. 검증 설계 (구현 전에 못 박아두기)

- **평가셋**: 프리미엄 기프트·전통 디저트 카테고리 레퍼런스 **8~12개 사이트**. 목록은 `data/refs.yaml`에 고정한다.
- **베이스라인은 PoC를 만들기 전에 측정한다.** 만들고 나면 기존 방식의 불편을 재현할 수 없다.
  - 사이트 3개를 평소 하던 대로 손으로 정리하며 시간을 잰다 → `data/baseline/`
  - 이때 만든 노트가 곧 정답 라벨이 된다 (카피·컬러·섹션 구조)
- **비교군 3개**
  - (A) 수작업 리서치 — 기존 방식
  - (B) 스크린샷을 VLM에 통째로 던져 "정리해줘" — 순진한 AI 사용 (중간 대조군)
  - (C) PoC 파이프라인 — DOM/OCR/VLM을 조건에 따라 갈아 끼우고 구조화
- (B)를 두는 이유: **"AI를 썼다"가 아니라 "어떤 설계가 몇 %를 만들었다"** 를 말하기 위해서다. 평가 5번(새로운 시도)의 근거가 여기서 나온다.

## 7. 범위 밖 (out of scope)

로그인이 필요한 페이지, 인스타그램·앱 전용 콘텐츠, 실시간 모니터링·알림, 이미지 자동 생성, 여러 사용자용 배포 서비스, 수집 대상 자동 발굴(후보 URL은 사람이 고른다).

## 8. 저작권·수집 원칙 (착수 전에 정한다)

리서치는 본질적으로 남의 결과물을 보는 일이라, 규칙을 먼저 정하고 시작한다.

1. **원본 스크린샷은 저장소에 올리지 않는다.** `.gitignore`로 막는다.
2. 저장소에는 **URL 목록 + 수집 스크립트 + 파생 데이터**(추출 텍스트, 컬러 값, 통계)만 커밋한다. 남이 실행하면 같은 결과가 재현되면서 타사 이미지는 재배포되지 않는다.
3. 공개 페이지만 대상으로 하고, `robots.txt`를 존중하며, 요청 간격을 둔다.
4. 문서에 실을 시연용 이미지는 **내 소유 자산(단정)** 또는 마스킹한 것만 쓴다.
