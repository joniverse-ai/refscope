# 모델 선정 & 근거

> Main Quest 2 제출물 2/4의 일부 (모델 선정 근거)
> 상태: 초안 (v0.1) — `[실측]` 표시는 내 데이터로 돌려본 뒤 채운다

파이프라인이 네 갈래이므로 선정도 네 번 한다. 각 갈래마다 **후보 → 비교 → 선택 → 왜**의 순서로 기록한다.

```
[오디오] ──① STT──▶ 타임스탬프 전사
[자료PDF] ─② 텍스트 추출──▶ 페이지별 텍스트
                     └──③ 임베딩 + 정렬──▶ 슬라이드별 발화 구간
                                        └──④ LLM 요약──▶ 노트
```

---

## ① STT (음성 → 타임스탬프 전사)

### 후보 비교

| 후보 | 한국어 품질 | 속도 (Apple Silicon) | 비용 | 데이터 위치 |
|---|---|---|---|---|
| **Whisper large-v3-turbo** | 한국어 CER 5.8% / WER 14.5% — large-v3보다 오히려 약간 우수 | mlx-whisper·whisper.cpp로 Metal 활용 | 무료 | 로컬 |
| Whisper large-v3 | CER 6.6% / WER 14.9% | turbo 대비 약 1/8 속도 | 무료 | 로컬 |
| Whisper small/medium | 한국어에서 품질 하락 뚜렷 | 빠름 | 무료 | 로컬 |
| 클라우드 STT API | 대체로 안정적 | 업로드 시간 | 분당 과금 | **외부 전송** |

구현체 선택도 함께 필요하다.

| 구현체 | Mac에서 |
|---|---|
| **mlx-whisper** | Apple Silicon GPU/Neural Engine(Metal) 사용 — Mac 최적 |
| whisper.cpp | Metal 지원, Python 의존성 없음, 약 10× 실시간 |
| faster-whisper | **Mac에서 Metal 미지원 → CPU 전용**, large-v3 약 3× 실시간 |
| openai-whisper (원본) | Colab GPU에서는 무난, Mac에서는 느림 |

### 선택: `Whisper large-v3-turbo` + `mlx-whisper` (로컬) / Colab GPU 백업

**왜 이걸 골랐나**

1. **한국어에서 turbo가 large-v3에 밀리지 않는다.** 2026년 벤치마크에서 한국어·일본어는 turbo가 오히려 소폭 우세했다. "가장 큰 모델이 항상 낫다"가 이 언어에서는 성립하지 않는다는 게 선정의 핵심 근거다.
2. **속도가 실험 횟수를 결정한다.** 이 PoC는 정렬 알고리즘을 A/B 해야 하므로 같은 오디오를 여러 번 돌린다. large-v3 대비 약 8배 빠른 turbo가 반복 실험을 가능하게 한다.
3. **Mac에서는 구현체가 성능을 가른다.** faster-whisper가 일반적으로 빠르다고 알려져 있지만 Mac에서는 Metal을 못 쓰고 CPU로 떨어진다. 같은 모델이라도 mlx-whisper/whisper.cpp가 맞다. — *커리큘럼 3회차 "내 노트북에서도 LLM이 돌아갈까"의 결론이 여기서 그대로 재현된다*
4. **녹음은 민감 데이터다.** 강의·회의 녹음에는 참석자 목소리와 발언이 들어간다. 로컬 실행이면 이 문제가 아예 발생하지 않는다. — *3회차 "데이터는 어디에 남는가"*

**기록해둘 실측치**: `[실측]` 1시간 오디오 전사 소요 시간 / WER (5분 구간, 직접 전사한 정답 대비)

**필요 옵션**: 세그먼트 타임스탬프는 기본 출력. 슬라이드 경계를 정밀하게 잡으려면 `word_timestamps=True`도 검토.

## ② 슬라이드 텍스트 추출

### 후보 비교

| 후보 | 언제 쓰나 | 정확도 | 비용 | 얻는 것 |
|---|---|---|---|---|
| **PDF 텍스트 레이어** (PyMuPDF) | PDF가 디지털 생성물일 때 | **무손실 (100%)** | 0 | 텍스트만 |
| OCR (PaddleOCR / Tesseract) | 스캔·이미지 슬라이드 | 조판·폰트에 따라 변동 | 0 | 텍스트만 |
| VLM (Qwen-VL, Claude, GPT 등) | 다이어그램·차트 설명이 필요할 때 | 텍스트는 OCR보다 약할 수 있으나 **그림을 설명함** | 로컬 무료 / API 과금 | 텍스트 + 시각 요소 서술 |

### 선택: **텍스트 레이어 먼저, 실패한 페이지만 OCR, 그림 많은 페이지는 VLM 보강**

**왜 이 순서인가**

1. **가장 중요한 판단: PDF에 텍스트 레이어가 있으면 OCR은 불필요하다.** 파워포인트·Keynote·LaTeX로 만든 PDF는 글자가 이미 데이터로 들어있다. 여기에 OCR을 돌리는 것은 정확한 원본을 흐릿한 사본으로 바꾸는 짓이다. 그래서 파이프라인 1단계는 모델이 아니라 **검사**다 — `page.get_text()`가 비어 있는 페이지만 OCR 대상으로 내린다.
2. **이 PoC의 목적은 텍스트 매칭이다.** 슬라이드를 발화에 배정하는 데 필요한 것은 그 페이지의 키워드다. 그림의 의미 서술까지는 정렬에 필수적이지 않다.
3. **다만 "그림만 있는 슬라이드"가 정렬의 약점이 된다.** 텍스트가 거의 없는 페이지는 임베딩이 비어 매칭이 실패한다. 이 페이지에만 VLM을 붙여 설명 텍스트를 생성하면 매칭 재료가 생긴다. → **한계 섹션의 핵심 소재이자, 개선 실험 하나가 여기서 나온다.**

*커리큘럼 4회차 "같은 PDF를 네 가지 눈으로 읽기"가 그대로 이 갈래의 실험 설계다.*

**기록해둘 실측치**: `[실측]` 텍스트 레이어 보유 페이지 수 / OCR 필요 페이지 수 / 텍스트가 N자 미만인 페이지 수

## ③ 임베딩 + 정렬 (이 PoC의 심장)

### 임베딩 후보

| 후보 | 한국어 | 실행 | 비고 |
|---|---|---|---|
| **BGE-M3** | MTEB 한국어 벤치마크 최상위권, 다국어 어휘 약 25만 토큰 | 로컬 (CPU도 가능, Colab 권장) | 다국어 강자 |
| **KURE** (고려대) | BGE-M3를 한국어로 추가 파인튜닝 | 로컬 | 한국어 검색 특화 |
| KoE5 / multilingual-e5-large | 한국어 파인튜닝 계열 | 로컬 | |
| OpenAI text-embedding-3 | 무난 | API | 전사문 전체 외부 전송 |

**선택: BGE-M3 (기본), KURE 비교 실험**

- 한국어 검색 성능이 검증된 로컬 모델이고, 강의 자료와 발화라는 **같은 도메인 안의 짧은 텍스트끼리** 매칭하는 작업이라 다국어 범용 임베딩으로 충분하다.
- 로컬 실행이라 ①과 동일한 프라이버시 논거가 유지된다. 전사문 전체를 외부로 보내지 않는다.
- KURE는 BGE-M3 기반의 한국어 파인튜닝판이므로, 두 모델을 같은 평가셋에 돌려 정렬 정확도를 비교하면 **파인튜닝이 내 도메인에서 실제로 도움이 되는지**를 숫자로 답할 수 있다. — *1회차 5절 "남이 배운 것을 물려받는 파인튜닝"*

### 정렬 알고리즘 (모델이 아니라 알고리즘 — 실험의 중심)

| 방식 | 방법 | 예상 약점 |
|---|---|---|
| **A. 유사도 argmax** (베이스라인) | 각 발화 세그먼트를 가장 유사한 슬라이드에 배정 | 용어가 반복되는 슬라이드에서 배정이 튄다 |
| **B. 단조 정렬 제약** (제안) | "시간이 흐르면 페이지 번호는 되돌아가지 않는다"는 제약 하에 DP로 전체 배정 최적화 (DTW 계열) | 발표자가 슬라이드를 되돌아가면 깨진다 |
| C. B + 되돌아감 허용 | 페널티를 주되 역행을 허용 | 복잡도 증가 |

**A vs B 비교가 곧 개선 효과 검증이다.** 같은 평가셋에서 정렬 정확도를 재면, "AI를 넣었다"가 아니라 "**어떤 아이디어가 몇 %를 만들었다**"를 말할 수 있다. 평가 5번(새로운 시도) 대응.

## ④ 요약 LLM

### 후보 비교

| 후보 | 품질 | 비용 | 데이터 위치 | 컨텍스트 |
|---|---|---|---|---|
| **Claude Haiku 4.5** (`claude-haiku-4-5`) | 슬라이드 단위 요약에 충분 | $1 / $5 per MTok | API | 200K |
| Claude Sonnet 5 (`claude-sonnet-5`) | 더 높은 품질 | $3 / $15 (2026-08-31까지 도입가 $2 / $10) | API | 1M |
| Claude Opus 5 (`claude-opus-5`) | 최상위 | $5 / $25 | API | 1M |
| 로컬 LLM (Ollama + Qwen 등) | 한국어 요약 품질 변동 | 무료 | **로컬** | 모델별 |

### 선택: **Haiku 4.5 (기본) + 로컬 LLM 비교 실행**

**왜**

1. **작업이 쉽다.** 이 단계의 입력은 이미 슬라이드 단위로 잘려 있는 짧은 발화 묶음이다. 1시간 전사문 전체를 한 번에 요약하는 게 아니라 슬라이드 한 장씩 처리하므로, 가장 저렴한 모델로도 충분하다. **파이프라인 앞단이 잘 나뉘어 있으면 뒷단 모델을 작게 쓸 수 있다** — 이게 설계상 이득이다.
2. **비용이 사실상 문제가 안 된다.** 1시간 강의 전사문은 수만 토큰 규모이고, Haiku 4.5 입력 $1/MTok 기준 1강분 처리는 센트 단위다. `[실측]`으로 실제 토큰 수와 금액을 기록한다.
3. **컨텍스트 설계가 필요하다.** 슬라이드마다 개별 호출하되 강의 전체 맥락(과목명, 앞 슬라이드 요약)을 함께 넣는다. 반복되는 앞부분은 **프롬프트 캐싱**으로 처리한다. — *2회차 "토큰 예산표와 컨텍스트를 직접 설계한다"*
4. **로컬 대조군을 반드시 만든다.** 요약 단계만 로컬 LLM으로 돌린 버전을 함께 두면, 전 파이프라인을 완전 로컬로 굴릴 수 있는지 답이 나온다. 사내 회의 녹음처럼 외부 전송이 불가능한 경우의 실행 가능성 판정이다. — *3회차 8절 "내 도메인의 실행 위치 결정문"*

## 실행 위치 결정문 (3회차 대응)

| 단계 | 실행 위치 | 근거 |
|---|---|---|
| ① STT | **로컬** | 녹음은 참석자 음성이 담긴 민감 데이터. 로컬이면 유출 경로 자체가 없다 |
| ② 텍스트 추출 | **로컬** | 텍스트 레이어·OCR 모두 로컬로 충분 |
| ③ 임베딩·정렬 | **로컬** | 전사문 전체를 외부로 보내지 않는다 |
| ④ 요약 | API (로컬 대조군 병행) | 유일한 외부 전송 지점. 완전 로컬 대안의 품질을 실측해 대체 가능성을 판정 |

> 결론: **①~③이 로컬이라는 점이 이 PoC의 구조적 장점**이다. 외부로 나가는 것은 ④의 짧은 텍스트뿐이고, 그마저도 로컬 대체 가능성을 검증한다. 사내 회의 녹음으로 확장할 때 이 표가 도입 판단의 근거가 된다.
