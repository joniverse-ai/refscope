# 모델 선정 & 근거

> Main Quest 2 · 제출물 2/4 (PoC 코드의 모델 선정 근거)
> 모든 수치는 이 저장소에서 직접 측정한 값이다. 재현 명령을 각 절에 적었다.

파이프라인이 네 갈래라 선정도 네 번 한다. 갈래마다 **후보 → 비교 → 선택 → 왜**의 순서로 쓴다.

```
[URL 목록]
   │
   ├─ ① 수집 ──────────── Playwright (모델 아님)
   │
   ├─ ② 읽기 경로 판정 ─── 규칙 (모델 아님) ← 여기서 잘못 고르면 뒤가 전부 틀어진다
   │        ├─ DOM에 글자 있음 → 무손실 추출
   │        └─ 통이미지        → ③으로
   │
   ├─ ③ 글자 추출 ──────── Apple Vision / PaddleOCR / EasyOCR / Qwen2.5-VL 비교
   │
   ├─ ④ 컬러 ───────────── k-means + CIEDE2000
   │
   └─ ⑤ 구조·톤 ────────── 나누기는 좌표, 이름·톤만 Qwen2.5-VL
            └─ ⑥ 패턴 ──── bge-m3 임베딩 + k-means
```

## ② 읽기 경로 판정 — 모델보다 먼저 오는 '검사'

이 PoC에서 가장 중요한 판단은 **모델을 고르는 것이 아니라 모델을 쓸지 말지 정하는 것**이었다.

DOM에 글자가 있으면 OCR을 돌리지 않는다. 브라우저가 이미 정확한 원본을 갖고 있는데
그것을 픽셀로 만들어 다시 읽는 것은 정확한 원본을 흐릿한 사본으로 바꾸는 짓이다.
그래서 파이프라인 1단계는 모델이 아니라 검사다. — *커리큘럼 4-6절 「같은 PDF를 네 가지 눈으로 읽기」*

### 판정 기준을 두 번 틀렸다

이 판정을 처음부터 맞게 만들지 못했다. 틀린 과정 자체가 이 도메인의 성질을 드러낸다.

**1차: 페이지 단위로 셌다** — "DOM 글자 수 ≥ 800이면 dom 경로".
교동한과 상세페이지(17,275px)가 `dom`으로 판정됐다. 그런데 실제로는 y=2,000~13,300 구간,
**페이지의 64%에 DOM 텍스트가 0자**였고 그 자리는 `500×8,555px` 통이미지 한 장이었다.
페이지 전체에서 긁힌 2,140자는 전부 헤더·푸터·약관이었다.

> **상세페이지에 상용구는 항상 있다. 페이지 단위로 세면 그것에 속는다.**
> → 세로 구간(band) 단위로 바꿨다.

**2차: 가로 피복률로 쟀다** — "이미지 넓이 ÷ 페이지 넓이 ≥ 0.45".
그 500×8,555 통이미지가 1,440px 페이지 폭의 **35%**밖에 못 덮어 임계값에 걸리지 않았다.

> **세로로 긴 이미지는 좁아도 그 구간의 전부다.**
> → 세로 피복률(구간 높이 중 콘텐츠 이미지가 덮은 비율)로 바꿨다.

최종 판정은 구간마다 두 가지를 **따로** 묻는다 — 글자가 있나 / 큰 그림이 있나.
둘의 조합이 판정이다(`dom` / `ocr` / `both` / `empty`). 구현: [`src/refscope/regions.py`](../src/refscope/regions.py)

### 판정 결과가 곧 도메인 근거

```bash
uv run refscope analyze
```

| 페이지 종류 | 개수 | 글자가 이미지에 갇힌 비율 (평균) |
|---|---|---|
| 브랜드 홈 | 7 | **2%** |
| 상품 상세 | 5 | **81%** |

**같은 사이트라도 홈은 OCR이 필요 없고 상세는 필수다.** 도구를 페이지마다 갈아 끼워야 하는
이유가 여기서 나온다. 이 표가 없었다면 "그냥 전부 OCR 돌리자"로 갔을 것이고, 홈 7개에서
정확한 DOM 원본을 버리고 흐릿한 사본을 얻었을 것이다.

## ③ 글자 추출 — 네 가지 눈으로 같은 조각 읽기

### 후보

| 후보 | 성격 | 설치 | 실행 위치 |
|---|---|---|---|
| **Apple Vision** | macOS 내장. 받을 모델이 없다 | pyobjc만 | 로컬 |
| **PaddleOCR** | 고전적 검출→인식 조립 라인 | paddlepaddle + 모델 | 로컬 |
| **EasyOCR** | 같은 계열, 인식 모델이 다름 | torch (~2.5GB) | 로컬 |
| **Qwen2.5-VL 7B** | VLM. 글자 너머를 말할 수 있다 | Ollama 6GB | 로컬 |

### 실험 설계

상세페이지 3개(교동한과·한품·강릉명일한과)의 **같은 조각 22개**에 네 엔진을 돌렸다.
정답은 사용자가 PoC를 보기 전에 손으로 적어둔 카피 13줄(`data/baseline/`)이다.

```bash
uv run refscope compare --only gyodong_manwol hanpoom_99flower hangamall_dao \
  --engines apple_vision paddleocr easyocr qwen2.5vl
```

**엔진을 각각 별도 프로세스에서 돌린다.** 한 프로세스에서 연달아 돌렸더니 EasyOCR이
Paddle의 `Tensor holds no memory` 오류로 죽어 **재현율 0%로 잘못 측정**됐다. 단독으로
돌리니 멀쩡히 동작했다. 비교 실험에서 이런 오염은 결론을 통째로 뒤집는다.

### 결과

| 엔진 | 재현율 | 추출 글자 | 교차확인 | 저신뢰 | 소요 | 사람 대비 |
|---|---|---|---|---|---|---|
| **apple_vision** | **13/13 (100%)** | 10,106자 | **86%** | 0% | **14s** | **191배** |
| easyocr | 13/13 (100%) | 13,402자 | 59% | **29%** | 110s | 23배 |
| qwen2.5vl | 13/13 (100%) | 13,260자 | 85% | 0% | **1,301s** | 2배 |
| paddleocr | 12/13 (92%) | 5,607자 | 91% | 0% | 163s | 16배 |
| *사람 (수작업)* | *13/13* | *120자* | — | — | *2,580s* | *1배* |

- **재현율** — 사람이 손으로 적어둔 카피를 놓치지 않은 비율
- **교차확인** — 그 글자를 다른 엔진도 읽었는가. **문자 3-gram** 집합으로 잰다
- **저신뢰** — 신뢰도 0.3 미만 줄의 비율. *참고용*

### 지표를 두 번 고쳤다

**저신뢰만으로는 공정하지 않다.** PaddleOCR은 `drop_score=0.5`로 낮은 것을 내부에서 이미
버리고 주므로 0%가 당연하고, Apple Vision은 신뢰도를 0.3/0.5/1.0으로 뭉뚱그려 준다.
엔진의 내부 임계값에 좌우되지 않는 지표가 필요해서 **교차확인**을 만들었다.

교차확인도 처음엔 줄 단위로 쟀는데, 그러면 **잘게 쪼개는 엔진이 유리해진다**
(PaddleOCR 줄당 6자 vs Apple Vision 13.6자 — 짧을수록 남의 문장에 포함되기 쉽다).
문자 3-gram으로 바꾸니 분절 방식에 좌우되지 않게 됐다.

### 선택: **Apple Vision (1순위) + PaddleOCR (타 OS 대체 경로)**

**왜**

1. **글자 수가 많다고 잘 읽은 게 아니다.** EasyOCR이 13,402자로 가장 많이 뽑았지만
   교차확인이 59%뿐이고 저신뢰가 29%다. 실제 출력을 보면 왜인지 분명하다 —
   `[유과] 쌀 우미 속 백려조 오냐 녹독자` (신뢰도 0.04). 한국어가 무너질 때 OCR은
   빈손으로 돌아오지 않고 **그럴듯한 헛것**을 만들어 온다. 글자 수만 세면 이 엔진이 1등을 한다.
2. **Apple Vision이 정확도·속도 양쪽에서 이겼다.** 재현율 100%, 교차확인 86%,
   그리고 14초. PaddleOCR보다 **12배**, VLM보다 **93배** 빠르다.
3. **VLM을 OCR로 쓰면 안 된다.** qwen2.5vl은 1,301초가 걸리는데 Apple Vision 대비
   정확도 이득이 없다(교차확인 85% vs 86%). 사람(2,580초)보다 겨우 2배 빠를 뿐이라
   **자동화의 의미가 사라진다.** VLM은 글자가 아니라 **글자가 아닌 것**에 써야 한다(⑤로).
4. **PaddleOCR을 버리지 않는 이유** — Apple Vision은 macOS 전용이라 재현성이 반쪽이다.
   PaddleOCR은 어디서나 돌고 교차확인 91%로 가장 보수적이다(확신하는 것만 내놓는다).
   그래서 **`--engine paddleocr`로 갈아 끼울 수 있게** 인터페이스를 통일해 두었다.
   구현: [`src/refscope/ocr.py`](../src/refscope/ocr.py)의 `Engine` 프로토콜.

**모델 크기가 답이 아니었다.** 7B VLM보다 OS 내장 OCR이 이 작업에서 낫다.
*— 커리큘럼 3회차 「내 노트북에서도 LLM이 돌아갈까」의 결론이 여기서 재현된다.*

## ④ 컬러 — k-means + CIEDE2000

### 후보

| 방법 | 문제 |
|---|---|
| 최빈색 히스토그램 | 흰 배경이 전부를 차지한다 |
| **k-means (선택)** | 대표색을 뽑되, 무채색 처리를 따로 해야 한다 |
| VLM에게 물어보기 | 아래 검증 참고 — **추측한다** |

### 선택: k-means(k=12) + 무채색 분리 + 면적 정렬

**왜**

1. **흰 배경이 픽셀의 58~67%다.** 그대로 돌리면 "이 브랜드의 색은 `#ffffff`"라는
   쓸모없는 답이 나온다. HSV 채도 ≤0.12를 무채색으로 따로 분류해 유채색을 먼저 보여준다.
2. **채점은 CIEDE2000으로 한다.** RGB 유클리드 거리는 사람 눈이 느끼는 차이와 어긋난다.
   사용자가 스포이드로 찍은 색과의 색차 ΔE≤10을 일치로 본다.
3. **VLM에게 색을 묻지 않는 이유** — 대조군 B에서 Qwen2.5-VL은 `#FFD700`, `#8B4513`,
   `#ADD8E6` 같은 **CSS 상투색**을 답했다. 실제 팔레트는 `#c6baac`, `#acc7d9`, `#525c47`였다.
   **픽셀을 세는 일은 픽셀을 세서 해야 한다.**

### 결과 (성공 기준 #3 달성)

```bash
uv run python -m refscope.compare_abc
```

사람이 찍은 3색 중 자동 팔레트 top-8 안에 든 수 — 세 사이트 **모두 2/3**.
합계 **6/9**. 순진한 VLM은 3/9. 구현: [`src/refscope/palette.py`](../src/refscope/palette.py)

## ⑤ 구조·톤 — 일을 쪼개서 각자 잘하는 것만 시킨다

이 갈래에서 배운 것이 이 저장소 전체의 설계 원칙이 됐다.

**처음엔 한 번에 시켰다** — "좌표 붙은 텍스트 목록을 줄 테니 섹션으로 묶어줘".
qwen2.5vl:7b는 묶지 않고 **입력 20줄을 그대로 20개 섹션으로 되뱉었다.**
나누는 일과 이름 짓는 일을 한꺼번에 시킨 것이 잘못이었다.

**고친 뒤:**

| 하는 일 | 누가 | 왜 |
|---|---|---|
| 카피 고르기 | **규칙** (글자 크기·위치) | 큰 글자가 곧 강조점이다. 모델이 필요 없다 |
| 구간 나누기 | **좌표** (y 간격 최댓값 k-1개) | 섹션이 바뀌면 반드시 여백이 생긴다. 결정적으로 잰다 |
| 이름 짓기 | **Qwen2.5-VL** (텍스트) | 언어 작업. 모델이 잘하는 일 |
| 톤 서술 | **Qwen2.5-VL** (그림) | **여기만 눈이 필요하다** |

톤 서술에는 **대조 시트**를 쓴다 — 44,491px 페이지를 세로로 6등분해 옆으로 붙인 한 장이다.
그냥 축소하면 아무것도 안 보이고, 조각내어 여러 번 물으면 전체 구성을 못 본다.
구현: [`src/refscope/synthesize.py`](../src/refscope/synthesize.py)

## ⑥ 임베딩 — bge-m3

### 후보

| 후보 | 한국어 | 실행 |
|---|---|---|
| **bge-m3** | MTEB 한국어 상위권, 다국어 | 로컬 (Ollama 1.2GB) |
| KURE | bge-m3의 한국어 파인튜닝판 | 로컬 |
| OpenAI text-embedding-3 | 무난 | **API — 전사문 외부 전송** |

### 선택: bge-m3

두 군데에 쓴다.

1. **섹션 채점** — 사람 "제품사용 Tip" ↔ 기계 "사용법·보관법"은 문자열로 못 맞춘다.
   코사인 유사도 ≥0.62를 같은 섹션으로 본다. ([`score_sections.py`](../src/refscope/score_sections.py))
2. **카테고리 패턴** — 카피 217줄을 묶어 소구점을 도출한다. ([`patterns.py`](../src/refscope/patterns.py))

여기서도 원칙은 같다. **묶는 일은 임베딩이, 이름 짓는 일만 LLM이 한다.**

API 임베딩을 쓰지 않은 이유는 ⑦과 같다.

## ⑦ 실행 위치 결정문 (커리큘럼 3회차 대응)

| 단계 | 실행 위치 | 근거 |
|---|---|---|
| ① 수집 | 로컬 | 브라우저가 내 기계에서 돈다 |
| ② 판정 | 로컬 | 규칙 |
| ③ 글자 추출 | **로컬** | Apple Vision은 OS 내장, PaddleOCR은 로컬 모델 |
| ④ 컬러 | 로컬 | k-means |
| ⑤ 구조·톤 | **로컬** | Ollama + Qwen2.5-VL 7B |
| ⑥ 임베딩 | **로컬** | Ollama + bge-m3 |

> **외부로 나가는 데이터가 없다.** 수집 대상 URL에 접속하는 것 말고는 네트워크를 쓰지 않는다.
> API 키가 필요 없고, 비용이 0이며, 리서치 대상이 무엇인지 어느 업체에도 남지 않는다.
>
> 경쟁사 리서치는 **무엇을 보고 있는지 자체가 전략 정보**다. "우리가 지금 어느 브랜드
> 20곳을 훑고 있다"가 외부 로그에 남는 것은 그 자체로 유출이다. 이 PoC가 전부 로컬인 것은
> 비용 문제가 아니라 그래서다. — *3회차 8절 「내 도메인의 실행 위치 결정문」*

## 요약 — 이 선정에서 반복된 원칙

1. **모델을 쓰기 전에 안 써도 되는지 검사한다.** (② DOM 우선)
2. **큰 모델이 답이 아니다.** 7B VLM보다 OS 내장 OCR이 93배 빠르고 더 정확했다.
3. **일을 쪼개서 각자 잘하는 것만 시킨다.** 나누기는 좌표, 이름 짓기는 LLM, 색은 픽셀.
4. **지표를 먼저 의심한다.** 글자 수·신뢰도·줄 단위 일치는 모두 엔진을 편들었다.
5. **비교 실험은 격리한다.** 한 프로세스에 몰아넣었다가 결론이 뒤집힐 뻔했다.
